## 1. Ассеты дублируются в каждую локаль ⚠️ главный

**Измерено:**

```
dist/ngportfolio/browser/en   6.0M
dist/ngportfolio/browser/ru   6.1M
dist/.../en/my-projects       3.6M
dist/.../ru/my-projects       3.6M   ← те же самые файлы
```

**Причина.** В `angular.json` один ассет-глоб:

```json
"assets": [{ "glob": "**/*", "input": "public" }]
```

`ng build --localize` прогоняет его для каждой локали, поэтому **весь** `public/` копируется и в
`/en/`, и в `/ru/`. В английскую сборку уезжают русские скриншоты, в русскую — английские, плюс оба
PDF-резюме и `og-image.png` в обе.

**Что делать.** Вынести тяжёлые статичные файлы в корень сайта (там, где уже лежат `robots.txt`,
`sitemap.xml` и `og-image.png` из `assemble-dist.mjs`) и ссылаться на них корнево-относительно:

1. перенести `public/my-projects/` и оба PDF из `public/` в отдельную папку (например `static/`),
   которую `assemble-dist.mjs` копирует **один раз** в `dist/ngportfolio/browser/`;
2. в `project-gallery.generated.ts` и в `PROFILE.resume` поменять пути на `/my-projects/...`
   и `/Alexey-Popov-Resume.pdf`;
3. в генераторе (`scripts/optimize-project-images.mjs`) поменять префикс `base` соответственно.

**Осторожно:** сайт живёт на `asdalexey.github.io/`, то есть корень домена совпадает с корнем
сайта. Если он когда-нибудь переедет в подпапку, корнево-относительные пути сломаются — тогда нужен
`<base href>`-осознанный хелпер. Сейчас это не так, но записать стоит.

**Выигрыш:** ≈ 5 МБ, то есть больше 40% веса деплоя.

## 2. `index.html` — 159 КБ, половина из них инлайновый CSS

**Измерено:** `index.html` (ru) = 159 КБ на диске, из них **76 КБ в 24 блоках `<style>`**.
Крупнейшие:

| Блок             | Размер | Что это                      |
| ---------------- | ------ | ---------------------------- |
| showcase         | 12 КБ  | панель-IDE в герое           |
| nav              | 6 КБ   | шапка + мобильная шторка     |
| hero             | 5 КБ   |                              |
| project-card     | 5 КБ   |                              |
| gallery-lightbox | 5 КБ   | **виден только после клика** |

**Почему так.** Angular инлайнит стили всех отрендеренных компонентов в пререндеренный HTML. Это
правильно для того, что видно сразу, и чистая потеря для того, что нет: стили лайтбокса, диалога
подтверждения в отзывах и конами-терминала едут в первом байте документа, хотя нужны по клику.

**Что делать.**

- обернуть тяжёлое-и-невидимое в `@defer (on interaction)` / `@defer (on viewport)` — их стили и
  код уедут в отдельный чанк (см. пункт 3);
- проверить `optimization.styles.inlineCritical` в `angular.json`: сейчас включено по умолчанию для
  production, и оно инлайнит критический CSS **дополнительно** к компонентным стилям;
- 146 HTML-комментариев (2 КБ) переживают сборку — `optimization.styles.removeComments` их не
  трогает, это комментарии в шаблонах. Мелочь, но при желании чистится.

**Выигрыш:** реалистично 159 → ≈ 90–100 КБ, то есть быстрее First Contentful Paint на медленной
сети.

## 3. Ни одного `@defer` на весь проект

**Измерено:** `grep -rn "@defer" src/app | wc -l` → `0`.
`main.js` = 452 КБ raw / **128 КБ gzip**.

Единственная ленивая загрузка в проекте — Swiper (182 КБ отдельным чанком, `registerSwiper()`),
и она сделана вручную через динамический `import()`.

**Кандидаты на `@defer`, по убыванию пользы:**

| Компонент                     | Триггер          | Почему                                                    |
| ----------------------------- | ---------------- | --------------------------------------------------------- |
| `app-gallery-lightbox`        | `on interaction` | нужен только после клика по превью, тянет за собой Swiper |
| `app-konami`                  | `on idle`        | пасхалка, которую 99% посетителей не увидят               |
| `app-testimonial-card` диалог | `on interaction` | `<dialog>` подтверждения открывается по кнопке            |
| `app-cursor`                  | `on idle`        | декор, не нужен в первом кадре                            |
| секция `app-recommendations`  | `on viewport`    | последняя на странице                                     |

**Осторожно:** `@defer` в пререндеренном приложении по умолчанию рендерит `@placeholder` в
статический HTML. Для SEO важно, чтобы текст отзывов остался в разметке — значит либо не деферить
секцию отзывов целиком, либо использовать `@defer (hydrate on viewport)` (Angular 19+,
incremental hydration), что как раз этот случай и решает.

## 4. `og-image.png` — 201 КБ

**Измерено:** `public/og-image.png` = 201 КБ, и он копируется трижды: в `/en/`, в `/ru/` и в корень
через `assemble-dist.mjs`. Итого 600 КБ ради картинки, которую видит только парсер соцсети.

**Что делать:** пережать. 1200×630 PNG с плоским тёмным фоном должен весить 30–50 КБ. Инструмент
уже в проекте — `sharp` стоит в devDependencies после добавления галерей:

```js
sharp('public/og-image.png').png({ quality: 82, compressionLevel: 9, palette: true });
```

Формат менять нельзя (часть краулеров не понимает WebP в `og:image`), но палитровый PNG даст 3–5×.

## 5. CI проверяет меньше, чем обещает README

README перечисляет гейты: ESLint, Prettier, Stylelint, Husky, madge, jscpd.
`.github/workflows/ci.yml` реально запускает **три**: ESLint, Stylelint, тесты с покрытием.

Не запускаются в CI:

- `bun run prettier:check` — форматирование ловится только husky-хуком, а он обходится `--no-verify`;
- `bun run madge` — циклические зависимости;
- `bun run jscpd` — дубликаты;
- Lighthouse — цифра 100 в бейдже README ничем не защищена от регрессии.

**Что делать:** добавить три шага в job `quality` (дешёвые, секунды) и отдельный job с
`treosh/lighthouse-ci-action` на собранном `dist`, с порогами 100/100/100 для A11y/BP/SEO
и, скажем, 90 для Performance.

## 6. PDF-резюме — 1 МБ на локаль

**Измерено:** `Alexey-Popov-Resume.pdf` 444 КБ + `Alexey-Popov-Resume-ru.pdf` 565 КБ, обе копии в
обеих локалях = **2 МБ деплоя**.

Резюме рендерится скриптом (`scripts/resume/render.sh`), то есть вес контролируемый. 500 КБ для
двухстраничного текстового PDF — это почти наверняка невстроенные подмножества шрифтов или
растровые картинки внутри. Стоит прогнать через `gs -dPDFSETTINGS=/ebook` и посмотреть, что
останется; ожидаемо 100–150 КБ.

Плюс пункт 1: после выноса в корень они перестанут дублироваться.

## 7. Шрифты: не баг, но лишний вес

Устройство сейчас (и оно **осознанное**, README это описывает):

- `public/fonts/*.woff2` — три самостоятельно нарезанных подмножества (`inter-latin`,
  `inter-cyrillic`, `jetbrains-mono-latin`), объявлены инлайном в `index.html` и **предзагружены**;
- `@fontsource-variable/inter` + `jetbrains-mono` из `angular.json` — полный набор, 13 файлов,
  **297 КБ** в `media/`.

Стек `--font` ставит самостоятельные подмножества первыми, fontsource — фолбэком для остального.
Благодаря `unicode-range` лишние подмножества **не скачиваются**, так что во время выполнения это
не стоит ничего.

Но: `latin-ext`, `greek`, `greek-ext`, `vietnamese` для EN/RU-сайта не запросят никогда, а в репо
и в артефакт они едут — и в обе локали.

**Что делать (аккуратно):** проверить, покрывают ли самостоятельные подмножества все реально
используемые глифы. Если да — выкинуть fontsource из `angular.json` целиком.

**Как проверить, а не угадать:** собрать без fontsource, открыть обе локали, в DevTools →
Rendering → включить «Emulate a focused page» и посмотреть вкладку Network на предмет
`font` с fallback, плюс глазами пройти по кириллице, `—`, `·`, `↗`, `✓` и `«»`. Именно на типографике
проще всего не заметить подстановку системного шрифта.

**Выигрыш:** ≈ 240 КБ репозитория и артефакта. Риск средний — поэтому пункт не первый.

## 8. Нет защиты от регрессий по весу

`budgets` в `angular.json` описывают только JS (`initial` 500 КБ / 1 МБ) и стили компонента
(10 / 14 КБ). Не покрыто ничем:

- вес картинок (сейчас `my-projects` 3.6 МБ; ничто не мешает уронить туда PNG на 4 МБ);
- размер `index.html`;
- суммарный вес деплоя.

**Что делать:** добавить в CI шаг, который считает `du -sb dist/ngportfolio/browser` и падает выше
порога. Пять строк bash, ловит целый класс регрессий.

Отдельно: бюджет `anyComponentStyle` в 10 КБ уже почти выбран `showcase.scss` (≈ 10.0 КБ). Любая
следующая правка этой панели упрётся в предупреждение. Стоит либо разделить компонент, либо
осознанно поднять порог — но именно осознанно, а не по факту падения сборки.

## Архитектура: что хорошо и трогать не надо

Чтобы в следующей сессии не «улучшили» то, что уже правильно:

- **zoneless + OnPush везде**, состояние на сигналах, DI через `inject()`. Ни одного `any`, ни
  одного `console.`, ни одного `TODO` во всём `src/`.
- **Вся моторика — CSS scroll-timelines**, ни одного слушателя скролла. `career-path`, `pipeline`,
  параллакс свечений в герое, курсорный хвост — всё либо на `view()`/`scroll()`, либо на одном
  `requestAnimationFrame`, который засыпает.
- **Каждый эффект дважды выключается** — и в JS (слушатель не навешивается), и в CSS
  (`prefers-reduced-motion`, `hover: none`). Это редко делают полностью; здесь сделано.
- **100% покрытие реально держится** (111 тестов), с порогом в `vitest-base.config.ts`. Istanbul
  инструментирует исходный TypeScript, а не вывод компилятора, — то есть цифра честная.
- **Локальный ESLint-плагин** (`eslint-local-plugin/`) кодирует конвенции проекта: приватные
  `#`-поля, DI только через `inject()`, запрет глобального `document`. Это редкость и это ценно.
- **Разделение слоёв** (`core` / `features` / `shared`) выдержано без протечек; `madge` циклов не
  находит.

Единственное архитектурное замечание — **`showcase` перегружен**: 791 строка SCSS и 340 строк
HTML в одном компоненте, который рисует табы, код, статус-бар, чипы и подсказку. Он не сломан, но
это самый вероятный источник будущей боли. Если руки дойдут — разнести на `panel-tabs`,
`panel-code`, `panel-status`.

## Порядок, в котором я бы это делал

1. **Пункт 1** (дублирование ассетов) — самый большой выигрыш на единицу риска.
2. **Пункт 5** (гейты в CI) — дёшево и защищает всё остальное от отката.
3. **Пункт 4 + 6** (og-image и PDF) — механическое сжатие, полчаса.
4. **Пункт 3** (`@defer`) — требует аккуратности с гидратацией, но окупается.
5. **Пункт 8** (бюджет на вес) — после того как вес приведён в порядок, зафиксировать его.
6. **Пункт 2 и 7** — последними: обе правки требуют проверки глазами в двух локалях.
